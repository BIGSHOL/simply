# TRD (기술 요구사항 정의서)

> 개발자/AI 코딩 파트너가 참조하는 기술 문서입니다.
> 기술 표현을 사용하되, "왜 이 선택인지"를 함께 설명합니다.

---

## MVP 캡슐

| # | 항목 | 내용 |
|---|------|------|
| 1 | 목표 | AdSense 부업 수익 창출을 위한 AI 심리테스트 플랫폼 |

### 1.2 컴포넌트 설명

| 컴포넌트 | 역할 | 왜 이 선택? |
|----------|------|-------------|
| Frontend (Next.js) | SSR/SSG로 SEO 최적화된 페이지 제공 | AdSense 수익을 위해 검색 유입 필수 |
| Backend (FastAPI) | API 서버, AI 호출, 비즈니스 로직 | Python으로 AI API 연동 용이, 비동기 지원 |
| PostgreSQL | 테스트, 결과 데이터 저장 | 안정적, JSON 필드 지원, 확장성 |
| Redis | 인기 테스트, AI 결과 캐싱 | 응답 속도 개선, API 비용 절감 |
| OpenAI API | 개인화된 테스트 결과 생성 | 가장 성숙한 AI API, 품질 보장 |

## 2. 권장 기술 스택

### 2.1 프론트엔드

| 항목 | 선택 | 이유 | 벤더 락인 리스크 |
|------|------|------|-----------------|
| 프레임워크 | Next.js 14 (App Router) | SSR/SSG로 SEO 최적화, 이미지 최적화 내장 | 중간 (Vercel) |
| 언어 | TypeScript | 타입 안정성, 자동완성, 버그 예방 | - |
| 스타일링 | TailwindCSS | 빠른 개발, 미니멀 디자인에 적합 | 낮음 |
| 상태관리 | Zustand | 간단하고 가벼움, 비로그인이라 복잡한 상태 없음 | 낮음 |
| HTTP 클라이언트 | Fetch API (native) | Next.js와 자연스러운 통합 | 없음 |

### 2.2 백엔드

| 항목 | 선택 | 이유 | 벤더 락인 리스크 |
|------|------|------|-----------------|
| 프레임워크 | FastAPI | 빠른 개발, 자동 API 문서, 비동기 지원 | 낮음 |
| 언어 | Python 3.11+ | AI 라이브러리 풍부, 빠른 개발 | - |
| ORM | SQLAlchemy 2.0 | 성숙한 ORM, 비동기 지원 | 낮음 |
| 검증 | Pydantic v2 | FastAPI와 통합, 빠른 검증 | 낮음 |
| AI 클라이언트 | OpenAI Python SDK | 공식 SDK, 안정적 | 중간 |

### 2.3 데이터베이스

| 항목 | 선택 | 이유 |
|------|------|------|
| 메인 DB | PostgreSQL 15+ | 안정적, JSON 필드로 AI 결과 저장, 확장성 |
| 캐시 | Redis | 인기 테스트 캐싱, AI 결과 캐싱으로 비용 절감 |

### 2.4 인프라

| 항목 | 선택 | 이유 |
|------|------|------|
| 프론트엔드 호스팅 | Vercel | Next.js 공식 지원, 무료 플랜 충분, CDN 포함 |
| 백엔드 호스팅 | Railway / Render | 저렴한 비용, Docker 지원, PostgreSQL/Redis 포함 |
| 컨테이너 | Docker + Docker Compose | 로컬/프로덕션 환경 일치 |

## 3. 비기능 요구사항

### 3.1 성능

| 항목 | 요구사항 | 측정 방법 |
|------|----------|----------|
| 페이지 로딩 | < 3s (FCP) | Lighthouse |
| API 응답 | < 500ms (일반), < 10s (AI 생성) | 서버 로그 |
| AI 결과 캐시 히트율 | > 30% | Redis 모니터링 |

### 3.2 보안

| 항목 | 요구사항 |
|------|----------|
| 인증 | 없음 (비로그인 서비스) |
| HTTPS | 필수 (Vercel/Railway 기본 제공) |
| 입력 검증 | 서버 측 Pydantic 검증 |
| Rate Limiting | IP 기반 제한 (AI API 남용 방지) |
| CORS | 허용 도메인만 설정 |

### 3.3 확장성

| 항목 | MVP | v2 목표 |
|------|------|--------|
| 동시 사용자 | 100명 | 1,000명 |
| 일일 방문자 | 3,000명 | 30,000명 |
| 테스트 개수 | 1~3개 | 20개+ |

## 6. 데이터 생명주기

### 6.1 원칙

- **최소 수집**: 개인정보 수집하지 않음 (비로그인)
- **익명 분석**: 분석용 데이터는 익명화
- **결과 캐싱**: AI 결과는 일정 기간 캐싱 후 삭제

### 6.2 데이터 흐름

```
테스트 진행 → 답변 해시 → AI 결과 생성/캐시 조회 → 결과 표시 → 공유
```

| 데이터 유형 | 보존 기간 | 삭제/익명화 |
|------------|----------|------------|
| 테스트 콘텐츠 | 영구 | - |
| AI 결과 캐시 | 30일 | 자동 삭제 |
| 방문 로그 | 90일 | 익명화 |
| 공유 링크 | 90일 | 자동 만료 |

## 7. 테스트 전략 (Contract-First TDD)

### 7.1 개발 방식: Contract-First Development

```
┌─────────────────────────────────────────────────────────────┐
│                    Contract-First 흐름                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 계약 정의 (Phase 0)                                     │
│     ├─ API 계약: contracts/*.contract.ts                   │
│     ├─ BE 스키마: backend/app/schemas/*.py                 │
│     └─ 타입 동기화: TypeScript ↔ Pydantic                  │
│                                                             │
│  2. 테스트 선행 작성 (RED)                                  │
│     ├─ BE 테스트: tests/api/*.py                           │
│     ├─ FE 테스트: src/__tests__/**/*.test.ts               │
│     └─ 모든 테스트가 실패하는 상태 (정상!)                  │
│                                                             │
│  3. Mock 생성 (FE 독립 개발용)                              │
│     └─ MSW 핸들러: src/mocks/handlers/*.ts                 │
│                                                             │
│  4. 병렬 구현 (RED→GREEN)                                   │
│     ├─ BE: 테스트 통과 목표로 구현                          │
│     └─ FE: Mock API로 개발 → 나중에 실제 API 연결          │
│                                                             │
│  5. 통합 검증                                               │
│     └─ Mock 제거 → E2E 테스트                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 테스트 피라미드

| 레벨 | 도구 | 커버리지 목표 | 위치 |
|------|------|-------------|------|
| Unit | pytest / Vitest | ≥ 80% | tests/unit/, src/__tests__/ |
| Integration | pytest / Vitest + MSW | Critical paths | tests/integration/ |
| E2E | Playwright | Key user flows | e2e/ |

### 7.3 테스트 도구

**백엔드:**
| 도구 | 용도 |
|------|------|
| pytest | 테스트 실행 |
| pytest-asyncio | 비동기 테스트 |
| httpx | API 클라이언트 |
| Factory Boy | 테스트 데이터 생성 |
| pytest-cov | 커버리지 측정 |

**프론트엔드:**
| 도구 | 용도 |
|------|------|
| Vitest | 테스트 실행 |
| React Testing Library | 컴포넌트 테스트 |
| MSW (Mock Service Worker) | API 모킹 |
| Playwright | E2E 테스트 |

### 7.4 품질 게이트

**병합 전 필수 통과:**
- [ ] 모든 단위 테스트 통과
- [ ] 커버리지 ≥ 80%
- [ ] 린트 통과 (ruff / ESLint)
- [ ] 타입 체크 통과 (mypy / tsc)

## 8. API 설계 원칙

### 8.1 RESTful 규칙

| 메서드 | 용도 | 예시 |
|--------|------|------|
| GET | 조회 | GET /api/v1/tests |
| POST | 생성/실행 | POST /api/v1/tests/{id}/submit |

### 8.2 응답 형식

**성공 응답:**
```json
{
  "data": { ... },
  "meta": {
    "cached": true,
    "generated_at": "2024-01-01T00:00:00Z"
  }
}
```

**에러 응답:**
```json
{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "잠시 후 다시 시도해주세요.",
    "retry_after": 60
  }
}
```

### 8.3 주요 API 엔드포인트

| 엔드포인트 | 메서드 | 설명 |
|------------|--------|------|
| /api/v1/tests | GET | 테스트 목록 조회 |
| /api/v1/tests/{id} | GET | 테스트 상세 조회 |
| /api/v1/tests/{id}/submit | POST | 테스트 답변 제출, AI 결과 생성 |
| /api/v1/results/{id} | GET | 결과 조회 (공유용) |

## 9. 병렬 개발 지원 (Git Worktree)

### 9.1 Worktree 구조

```
~/projects/
├── simly/                 # 메인 (main 브랜치)
├── simly-test-be/         # Worktree: feature/test-be
├── simly-test-fe/         # Worktree: feature/test-fe
├── simly-result-be/       # Worktree: feature/result-be
└── simly-result-fe/       # Worktree: feature/result-fe
```

### 9.2 명령어

```bash
# Worktree 생성
git worktree add ../simly-test-be -b feature/test-be
git worktree add ../simly-test-fe -b feature/test-fe

# 테스트 통과 후 병합
git checkout main
git merge --no-ff feature/test-be
git merge --no-ff feature/test-fe

# Worktree 정리
git worktree remove ../simly-test-be
```
